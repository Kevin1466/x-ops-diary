# 关键决策记录

只记录**改起来很贵**的决定。格式：背景 → 决定 → 代价 → 什么时候该重新考虑。

---

## D-001 · 用搜索 API 而不是 RSS 做信源

**背景**：需要覆盖 5 个板块、约 20 个信源。RSS 方案要维护 20 个解析器，官方博客一改版就断；X 账号还要过 RSSHub，稳定性和限流都不可控。

**决定**：用 DeepSeek 的网页搜索接口（`/v1/tools/search`），每个板块 1–2 条检索式，一次探测 10 次请求，约 $0.0075。

**代价**：按次计费；检索质量取决于检索式写得好不好；拿不到“社区互动增速”这类信号，只能改用接口返回的 `rerank_score` / `authority` 做替代。

**重新考虑的信号**：某板块的检索结果连续两周明显跑偏，或者单日成本超过 $2。

## D-002 · 发帖走浏览器自动化，不走官方 API

**背景**：官方 API 需要 OAuth 应用 + 付费档位；当前是单账号、每天 2–4 条。

**决定**：用扩展在 `x.com/compose/post` 上填字并点击发布。

**代价**：依赖页面结构（`data-testid` 会变）；Chrome 必须开着；有账号风险；失败时可能“发了但没确认”。

**重新考虑的信号**：日发帖量超过 10 条，或者需要 24 小时数据回流（官方的分析接口更省事）。

---

## D-003 · 审批用 5 分钟倒计时，而不是“必须人工确认”

**背景**：纯人工确认 = 没有自动化；纯自动发布 = 无人审核。

**决定**：候选推送到独立小窗，5 分钟倒计时，超时后按阈值自动发最高分；第一周阈值 60 且自动发送默认关闭。

**代价**：仍然可能把错的素材发出去；需要额外的“发布结果未知”兜底。

**重新考虑的信号**：连续出现两次误发，就把自动发送永久关掉，改成“只推送不发布”。

---

## D-004 · 这个仓库只放日记、数据、方法论，不放工具代码

**背景**：build in public 的常规做法是把代码也开源。

**决定**：代码另放。这里只记录“为什么这么做”和“做完效果如何”。

**代价**：少了一部分 star 来源。

**重新考虑的信号**：有人明确表示想看实现细节，再单独开一个干净的仓库。
